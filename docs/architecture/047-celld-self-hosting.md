# ADR 047: Self-hosting on celld alongside Cloudflare

- **Status:** Accepted
- **Date:** 2026-10-16
- **Keeps:** ADR 004 (CI/CD and deployment safety), ADR 008 (full-stack app on a single Worker)
- **Related:** `docs/self-hosting-celld.md` (operator runbook), `scripts/build-celld-config.mjs`, `scripts/deploy-celld.mjs`

## Context

Wrangnarok is Cloudflare-native by design (AGENTS.md: "Do not hide
Cloudflare behind a portability abstraction"). The question this ADR
answers is whether the same Worker can also run self-hosted, on an
operator's own machines, without forking the application or introducing
a runtime abstraction layer.

celld (https://celld.dev, Deno team's self-hosted Workers runtime,
v0.6.2 beta at decision time) runs a Wrangler-configured application --
Workers, Durable Objects, D1, R2, Workflows, Cron Triggers, and static
assets -- as distributed Durable Object "cells" backed by an operator
bucket (S3-compatible, GCS, or Azure Blob). It is not raw workerd:
open-source workerd has no D1, R2, or Workflows engine, so targeting
workerd directly would mean building that platform ourselves.

## Decision

Support exactly two deployment targets for the same Worker bundle:

1. **Cloudflare (hosted, unchanged).** `wrangler.jsonc` remains the
   single authored source of truth; `wrangler deploy --env dev` and the
   ADR 004 ladder remain the hosted path.
2. **celld (self-hosted, additive).** `npm run config:celld` derives
   `wrangler.celld.jsonc` from `wrangler.jsonc`; `npm run deploy:celld`
   deploys it to a celld fleet. No `src/` code changes, no binding
   abstraction, no second Saga/Execution path: celld supplies the same
   native bindings (`DB`, `FILES`, `ARTIFACTS`, `OAUTH_REFRESH_FENCE`,
   the 13 Workflow bindings, `ASSETS`) under the same names.

Mechanics that keep this honest:

- **Generated, never hand-edited.** celld rejects every top-level
  Wrangler key it does not list (`routes`, `observability`,
  `workers_dev`, `env`, ...), so the celld config is a filtered
  projection of the hosted top level, regenerated by
  `scripts/build-celld-config.mjs` and checked by `npm run check:celld`.
  That check runs as a non-gating CI job: celld drift is reported, but
  it can never block the hosted Cloudflare path (matching the
  consequence below). Cloudflare `env.*` blocks never project.
- **Secrets stay out of committed config.** celld has no secret store:
  deployed vars come only from the deployed config, which celld
  persists in the fleet bucket. `scripts/deploy-celld.mjs` therefore
  merges a gitignored operator vars file (`.celld.vars`) into a
  gitignored deploy config (`wrangler.celld.deploy.jsonc`) at deploy
  time. The committed `wrangler.celld.jsonc` carries non-secret vars
  only, exactly like `wrangler.jsonc`.
- **D1 migrations stay single-path.** The same `migrations/` directory
  applies through `wrangler d1 migrations apply` on Cloudflare and
  `celld d1 migrations apply wrangnarok-local` on celld
  (`deploy:celld --migrate`). No schema fork.

## Known celld deltas (verified against celld v0.6.2 docs, 2026-10-16)

- No TLS termination and plaintext peer traffic: an ingress proxy and a
  private/encrypted node network are operator responsibilities.
- No Windows binary: operators run Linux/macOS (WSL2 or Docker on
  Windows workstations).
- `observability` (Workers Logs/traces sampling) has no celld
  equivalent; celld telemetry replaces it on that target.
- Cloudflare Access is not in front of a self-hosted fleet, and this
  ADR does not amend ADR 014: fixture LAB auth stays local/CI and
  non-production, so on celld it serves local development and trusted
  trial fleets only. Production human sign-in requires an ingress
  injecting a verifiable `Cf-Access-Jwt-Assertion` into the
  `src/access.ts` path, or a future ADR for self-hosted identity.
- Cron Triggers are supported, but the hosted config currently ships
  `crons: []` (ADR 012 pause), so `scheduled` stays dormant on both
  targets until re-enabled.
- Workflow fidelity (per-step `retries.limit` including 0 for vendor
  steps, the 10s step timeout, `createBatch` retained-ID dedup, and
  `status()` values) is a documented celld surface but must be proven
  per pinned celld release by the smoke runbook before a fleet carries
  real tenants. The `system.smoke` Saga is the proof vehicle. On
  v0.6.2 (2026-10-16, single-node fleet over an S3-compatible bucket)
  the smoke proof passed end to end: all 42 migrations applied through
  `celld d1 migrations apply`, submit answered 202, the Execution
  reached `Succeeded` with `dispatchConfirmed`, a same-key resubmit
  replayed the same Execution (`replayed: true`), and the native
  status read back `complete`. Per-step retry/timeout behavior under
  vendor failure remains unproven and is part of the per-release smoke.

## Consequences

- Positive: one bundle, one bindings surface, two hosts; the
  Cloudflare-native experiment (ADR 001-046) is untouched, and Free-tier
  viability work keeps its meaning on the hosted target.
- Evidence scope: the v0.6.2 proof is a single-node fleet over a test
  S3-compatible store with LAB Bearer auth and the `system.smoke` Saga.
  Multi-node failover, ingress/Access-backed tenant auth, R2-heavy and
  Durable Object paths, and vendor-failure retry behavior follow
  celld's own guarantees and must be re-proven per release and per
  operator topology; this ADR does not claim them.
- Cost: a second deployment target to smoke and keep honest. The drift
  check runs as a non-gating CI job; the runtime smoke is operator-run
  per release until celld stabilizes enough to gate merges on it.
- If celld's Workflow semantics diverge in a way smoke exposes, the
  celld target degrades to "unsupported for that release" -- the hosted
  path is never blocked on celld.
